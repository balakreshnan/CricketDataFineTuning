# Olympics reasoning: Dynamo distillation + Nemotron-3.5-Lightning full SFT (Ptyche, GB200)

End-to-end pipeline that turns the 120-year Olympics athlete table into a **one-row-per-source-row reasoning
dataset**, generated by `nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16` served with **NVIDIA Dynamo (SGLang
backend)**, then **full-parameter fine-tunes the same model** on it with Megatron-Bridge across 16 GB200 GPUs,
evaluates base vs fine-tuned through Dynamo, and publishes both to Hugging Face with all metrics in W&B.

| Artifact | Link |
|---|---|
| Distilled dataset (public) | [Balab2021/Olympics-Reasoning-Nemotron-3.5-Lightning](https://huggingface.co/datasets/Balab2021/Olympics-Reasoning-Nemotron-3.5-Lightning) rev `5a19981` |
| Fine-tuned model (private) | [Balab2021/Nemotron-3.5-Lightning-30B-A3B-Olympics-Reasoning](https://huggingface.co/Balab2021/Nemotron-3.5-Lightning-30B-A3B-Olympics-Reasoning) rev `5b9c66c` |

**Interpretation.**
- **What improved:** on the distribution it was trained on, the model got slightly more accurate. Its reasoning

## 3. How the data was distilled

### 3.1 Verifiable questions, one per source row (`rows_qa.py`, `prep_rows.py`)
Every unique row of `athlete_events.csv` is one athlete's entry in one event at one Games. Each row anchors **one
question that names that athlete**. The context table is one of two kinds:

* **Event context (default):** the event's full entry list at that Games, when it has ≤ 150 entrants and the
  athlete's name is unique in it. Columns: Name, NOC, Age, Height, Weight, Medal.
  * `ev_same_noc`: entrants from the athlete's NOC.
  * `ev_older` / `ev_taller`: entrants older or taller than the athlete.
  * `ev_noc_medal_count`: medal rows won by the athlete's NOC.
* **Athlete context (fallback):** the athlete's career record (≤ 80 rows).
  * `at_events_at`: events entered at that Games.
  * `at_medals_at`: medals won at that Games.
  * `at_events_before`: events entered in earlier years.
  * `at_other_events_at`: events at that Games other than this row's event.

The gold answer is computed exactly from the table, so every answer can be checked. A row hash picks the template;
if that prompt is already taken, the next template is used, so every prompt is distinct. Each table has a fixed row
order, so all questions about one event share the same prompt prefix, which Dynamo's KV-aware router reuses.
Split: rows of athletes that hash into the 10 % test set go to `test`.

The answer format is `Final answer: <n>`, using this system prompt: *"You are a sports data analyst. Use only the
table you are given. Work through the problem step by step, then give the final answer on its own line as 'Final
answer: <answer>'."*

> One template was retired. The first wording of the NOC-medal question ("How many medal rows … (count every row,
> …)") was read by the model as "rows of that NOC" and scored 30 % pass@1. It was reworded to
> `ev_noc_medal_count` (96.7 % pass@1), and all 124,732 samples of the old wording (31,183 questions × 4) were
> discarded.

### 3.2 Serving the teacher with Dynamo (`gen.sbatch`)
Each node runs its own Dynamo deployment:
* `python -m dynamo.frontend --http-port 8000 --router-mode kv` provides an OpenAI-compatible API with a KV-cache-aware router.
* There are 4 × `python -m dynamo.sglang` workers, one per GPU, using TP1 (the 30B-A3B model fits on one GB200).
  They use the model card's Blackwell settings: `--mamba-backend flashinfer --mamba-ssm-dtype float16
  --enable-mamba-cache-stochastic-rounding --mamba-cache-philox-rounds 5`, plus `--mem-fraction-static 0.85
  --context-length 32768 --cuda-graph-max-bs-decode 256 --dyn-reasoning-parser nemotron_v3`.
* Discovery uses a node-local file store (`DYN_DISCOVERY_BACKEND=file`, `DYN_REQUEST_PLANE=tcp`,
  `DYN_EVENT_PLANE=zmq`), so no etcd or NATS is needed. Startup takes about 3.5 min.
* `gen_client.py` shuffles and shards the questions across nodes, keeps 512–1,024 requests in flight per node,
  samples K times per question (T=1.0, top_p=0.95, `chat_template_kwargs.enable_thinking=true`), grades each sample
  against the gold answer, and appends JSONL. Runs are resumable on `(id, sample)`.
* Throughput was **about 31.7k output tokens/s per 4-GPU node** on the 12-node first pass (380k tok/s in total) and up to 34k on long-trace retries; see §3.4.

### 3.3 Rejection sampling until (almost) every row is covered (`build_dataset.py`, `data.sbatch`)
For every source row, the **shortest trace that is verified correct, finished (not truncated) and at most 28k
tokens** across all of its questions is kept. Rows without one get more samples, then a different question:

| Pass | Questions | K | Max tokens | Nodes × time | Rows covered after |
|---|---|---|---|---|---|
| First pass, all rows | 269,731 | 4 | 16,384 | 12 × 2 h 03 m | 248,559 (92.2 %)¹ |
| Retry: unsolved + reworded template | 40,752 | 6 | 16,384 | 8 × 1 h 29 m | 263,793 (97.8 %) |
| Fallback: next template | 5,938 | 8 | 16,384 | 4 × 55 m | 268,585 (99.58 %) |
| Retry2: all questions of unsolved rows | 2,292 | 16 | 28,000 | 4 × 1 h 34 m | 269,543 (99.93 %)² |
| Fallback2: third template | 188 | 16 | 28,000 | 4 × 9 m | **269,723 (99.997 %)** |

¹ Counted with the old ambiguous NOC wording; 31k of those rows were then regenerated.
² Includes raising the dataset trace cap from 12k to 28k tokens; many hard rows only have long correct traces.

In total **1,410,620 Dynamo requests** (5.04B output + 1.57B prompt tokens; 2.63B output tokens in the first pass,
the rest in the long-trace retries) went into the 269,723 kept traces. Counting smoke tests, the table set and the
fine-tuned evaluation, the project made **1,604,344 requests (≈ 5.40B output tokens) with zero failed requests**. Across all row
samples, pass@1 was 86.3 % and 5.8 % were truncated. Per-type pass@1 ranged from 99.9 % (`at_medals_at`) down to
51 % (`ev_older`). The upload step refuses to run below 1:1 unless `--allow-missing N` is passed; it was run with
`--allow-missing 8` after the owner approved.

is not published. Its 550 test questions are the out-of-distribution benchmark, and its train traces were used
only for the training benchmark.

## 4. How it was fine-tuned on multiple GPUs

### 4.1 Data → packed sequences
* SFT files are written by `build_dataset.py`. Each row is a 3-turn chat: system, user, and an assistant turn with
  `reasoning_content` set to the trace and `content` set to the answer. Nemotron's chat template renders this as
  `<think>…</think>Final answer: …`. Loss is on the assistant turn only (`loss_mode="assistant"`).
* Rows with prompt + trace over 8,000 tokens are dropped from SFT; 12,403 rows (5.4 %) were dropped. They stay in
  the published dataset.
* 1 % of training rows are held out for validation loss.
* Training used a **frozen snapshot** (`data/sft-rows-v1`) taken at 99.58 % coverage, so training could run while
  the last rows were still being generated: **227,051 training + 2,237 validation rows**.
* Offline packing into **8,192-token sequences** produced 50,446 packed sequences, taking 1 h 25 min with a single
  tokenizer worker.

### 4.2 Parallelism (benchmarked first, `submit.sh bench`)
| Config (8k packed, gbs 32) | Step | TFLOP/s/GPU | Peak mem |
|---|---|---|---|
| 1 node, TP1, EP4, selective recompute (DeepEP or alltoall) | OOM at 171 GB/184 GB | – | – |
| 2 nodes, TP1, **EP8**, selective recompute, alltoall | 3.40 s | 259 | 122 GB |
| 2 nodes, TP1, **EP8**, selective recompute, **HybridEP** | **3.07 s** | **287** | 122 GB |

The production run used **4 nodes = 16 GB200** with TP1, PP1, CP1, **EP8** (the 128 experts split over 8 GPUs, so
each expert group is replicated across the 2 halves), DP 16 for the dense and Mamba parts, ETP1, and selective
recompute on `moe, layernorm, core_attn, mlp`. The MoE token dispatcher is the flex dispatcher with **HybridEP**,
which is built for GB200 NVL72; the recipe's DeepEP rejects the "NVIDIA GB200" device name. Peak allocation was
97 GB per GPU and steps took about 3.3 s at roughly 270 TFLOP/s/GPU.

### 4.3 Hyperparameters (`train.py` on top of `nemotron_3_5_lightning_sft_config`)
| | |
|---|---|
| Global / micro batch | 64 packed sequences / 1 |
| Sequence length | 8,192 |
| LR | 5e-6, cosine to 5e-7, warmup 30 steps |
| Epochs | 1 (789 steps) |
| Validation | every 100 steps, 10 iters |
| Checkpoints | every 100 steps, keep 2, with optimizer state (859 GB on Lustre) |
| Precision | BF16 (recipe default, distributed optimizer) |

Loss: training loss went 0.106 (step 10) → 0.096 (step 400) → 0.095 (step 785). Validation loss went 0.1013 → 0.1045
(step 200) → 0.0995 (step 600) → **0.0973** (final). All of these are logged to W&B.

## 5. Reproducing it

Everything below runs from the login node through the bridge (`px`). Jobs that need many CPUs, GPUs or enroot go to
compute nodes, because the login node kills long CPU-heavy processes and cannot run `enroot import`.

```bash

& 'C:\Program Files\Git\bin\bash.exe' ptyche/bin/ptyche-bridge     # complete MFA, keep window open
bash ptyche/bin/psync                                              # ptyche/ -> /home/bbalakreshna/clustercodes

# 1. secrets on Lustre (user, own SSH session): HF_TOKEN (write), WANDB_API_KEY, WANDB_ENTITY
#    /lustre/fsw/general_sa/bbalakreshna/secrets.env  (chmod 600)

# 2. one-off setup
bash ~/clustercodes/olympics/setup_login.sh          # tools venv + model download (its enroot step fails on login)
sbatch -p tcpo ~/clustercodes/olympics/setup.sbatch  # import Dynamo-SGLang + NeMo images (aarch64) on a compute node
#    source data: athlete_events.csv / noc_regions.csv at rev 6b64cef -> $DATA_DIR/olympics-dataset/

# 3. questions
set -a; source ~/clustercodes/olympics/config.env; set +a
$TOOLS_VENV/bin/python $CODE_DIR/prep_questions.py   # 9.8k table set (benchmark)  -> data/questions_{train,test}.jsonl
sbatch -p tcpo $CODE_DIR/rows.sbatch                 # 269,731 row questions       -> data/questions_rows_{train,test}.jsonl

# 4. distillation with Dynamo
K=8 TAG=full sbatch -p tcpo -N 4 -t 02:30:00 --export=ALL $CODE_DIR/gen.sbatch
K=4 TAG=rows SPLITS="rows_test rows_train" CONCURRENCY=1024 sbatch -p tcpo -N 12 -t 04:00:00 --export=ALL $CODE_DIR/gen.sbatch

# 5. base checkpoint for Megatron
```

## 6. Did fine-tuning add knowledge to the model?

**Essentially no, and it wasn't designed to.** This was *self*-distillation:

1. **The teacher is the student.** Every trace was written by the same base model, so the training data contains
   nothing the model could not already produce. Rejection sampling only keeps the samples where it happened to be
   right and short. SFT on those samples **sharpens** the model's own distribution towards the successful,
   concise reasoning paths it already had. That is a skill or behaviour change, not new knowledge.
2. **Every answer is in the prompt.** Each question includes the full table it needs, and the system prompt says
   "use only the table you are given". The model is rewarded for reading and counting carefully, not for recalling
   facts. Any Olympic facts it absorbed from 227k in-context tables would be incidental. No closed-book evaluation
   (asking without the table) was run, so nothing here shows that it memorised them.
3. **The measured effects look like skill, not knowledge.** Reasoning is 12 % shorter, there are fewer runaway
   traces, and accuracy rose slightly on the hard counting types it trained on. Accuracy fell slightly on
   table-question types it did not train on. Added knowledge would show up as gains on new facts, which these
   benchmarks do not measure; the pattern seen is typical of narrow behavioural fine-tuning.

To actually add knowledge you would need **closed-book** training pairs (for example, "How many medals did X win
at the 1988 Games?" with no table), ideally with answers the model cannot already produce, evaluated closed-book on
held-out facts. Even then, SFT is a weak and lossy way to store a 270k-row table; retrieval (RAG over the CSV) or a
tool call is the usual answer for factual lookups.

## 7. Known limitations and next steps
* The hardest traces (prompt + trace over 8k, 12.4k rows) and the last 1,138 rows solved after the snapshot were
  not trained on. Re-training with **16k packed sequences** on the final dataset should help most on
  `ev_older`/`ev_taller`.
* Mixing in the table-question types (`country_golds`, `sport_top_country`) should remove the out-of-distribution
  regression.
* The base model is already at about 92 % on this task, so the ceiling for self-distillation is low. A stronger
  teacher (a larger Nemotron) or RL with the exact-answer verifier (NeMo RL, GRPO) would be the next lever.

## 8. Gotchas we hit (all fixed in the code)
* The login node kills long CPU jobs and cannot `enroot import` (capabilities): use compute nodes.
* Inside `bash -c '…'` blocks in job scripts, a single apostrophe in a comment breaks the whole job.
* **Megatron-Bridge's offline-pack cache ignores the data**: `<tokenizer>_pad_seq_to_mult2_sft_<hash>` collides
  across datasets and silently reuses the old pack. `train.py` now packs through a per-dataset tokenizer symlink
  (`<data>/tokenizer`).
* Packing about 230k rows with one tokenizer worker takes over 1 h on Grace, so give the pack job a 4 h limit.
* The recipe's DeepEP refuses "NVIDIA GB200": use `--dispatcher hybridep`. 1 node (EP4) OOMs, so use at least 2
  nodes with EP8.
* `scontrol update` cannot move pending jobs between partitions here (time-limit error): cancel and resubmit.
  `batch` was blocked by a reservation; `tcpo` worked.
* `pkill -f <name>` inside a `bash -c` that contains `<name>` kills its own job step: kill by PID.
* A question wording the model reads differently from the grader looks like low accuracy. Inspect failures
  (`inspect_gen.py`) before resampling.

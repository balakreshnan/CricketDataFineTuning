Olympics reasoning: distill with Dynamo, fine-tune on GB200

A reasoning dataset was built from 120 years of Olympic entries, with one verified trace for each source row. The traces were generated by Nemotron-3.5-Lightning-30B-A3B served with NVIDIA Dynamo (SGLang backend), and the same model was then full-fine-tuned with Megatron-Bridge on 16 GB200 GPUs. The idea

  • Verifiable questions: each source row (one athlete's entry in one event) gets one question built over a table taken from the data, and its gold answer is computed exactly.
  • Rejection sampling: the model answers each question several times, and only the shortest correct trace is kept.
  • Self-distillation: the same model is the teacher, the student and the baseline.

Distillation: from a source row to a verified trace

1 · One question per source row

Each row anchors one question that names the athlete. The context is either the event's entry table (up to 150 entrants) or the athlete's career table (up to 80 rows).

TemplateAsksDataset rowspass@1

Each event table keeps a fixed row order, so all questions about one event share the same prompt prefix, which the KV-aware router can reuse.

One template was retired. The first wording of the NOC-medal question ("medal rows … count every row") was read by the model as "rows of that NOC" and scored 30 %. It was reworded (96.7 %) and all 124,732 samples of the old wording were discarded. Checking failures before resampling saved a lot of GPU time.
The last 8 rows were counting questions over 100-plus-entrant team rosters that no sample got right across 3 templates and 60-plus samples per row. They were accepted as a known shortfall and are listed in the dataset card.

How Dynamo was parallelised

Across nodes

Every node runs its own Dynamo deployment with a file-based discovery store, so it needs no etcd or NATS. Questions are shuffled and sharded by index % N. Nodes never talk to each other, so throughput scales linearly.

Inside a node

There are 4 SGLang workers, one per GPU, each holding a full copy of the 30B-A3B model (about 60 GB of 189 GB). The frontend's KV-aware router sends requests that share a prompt prefix to the worker that already has it cached.

Inside a GPU

Continuous batching keeps about 256 requests in flight per GPU (1,024 per node). Each GPU has about 8.7 M tokens of KV/Mamba-state capacity, and the decode CUDA graph is sized to batch 256.

Across GPUs during fine-tuning

Megatron logs averages across ranks. W&B recorded per-GPU system metrics every ~7.5 s on one training node. Its four GPUs behaved almost identically, so the expert-parallel load was balanced.

Reading it

  • GPUs were busy (81–84 %) but only about 12 % tensor-pipe active, at half the power limit. The run is bound by small expert GEMMs, Mamba scans, recompute and all-to-all traffic, which is typical for a model with about 3 B active parameters.
  • The MoE load-balance loss stayed near 1.0 (1.05 → 0.98), so tokens were spread evenly over experts. That matches the flat per-GPU power and NVLink traffic.
  • Megatron's rank-0 peak was 96.9 GB allocated, and NVML saw about 109 GB per GPU. That leaves about 80 GB free, enough for 16k sequences next time.

Reading the results

  • In-distribution: slightly more accurate, with 12 % shorter reasoning and fewer runaway traces. The largest gains were on the hard counting types (taller +1.6, older +1.2 points).
  • Out-of-distribution: the two country-medal tally types dropped by 2.7–4.3 points, about 2 standard errors on 550 questions. Mixing those types into training should fix this.
  • Small headroom: the base model was already at about 92 %, the hardest traces (longer than 8k tokens) were excluded from SFT, and the student learned only from itself.

Did fine-tuning add knowledge to the model?

Essentially no, and it wasn't designed to. This run changed how the model reasons over the table it is given. It did not teach it new facts.

1 · The teacher is the student

Every trace was written by the same base model. Rejection sampling kept only its own correct, short attempts. SFT sharpens the model towards reasoning paths it could already produce.

2 · Every answer is in the prompt

Each question includes the full table it needs, plus the instruction "use only the table you are given". The model is rewarded for careful reading and counting, not recall. No closed-book test was run.

3 · The effects look like skill

Reasoning got 12 % shorter, there were fewer truncations, accuracy rose slightly in-distribution, and it fell slightly on unseen question types. This is the signature of narrow behavioural fine-tuning.

To actually add knowledge

  • Train on closed-book pairs (for example "How many medals did X win in 1988?" with no table), using facts the model cannot already answer, and evaluate closed-book on held-out facts.
  • For lookups over a 270k-row table, retrieval or a tool call is usually better than putting the table into the weights.
  • For more reasoning skill: a stronger teacher, or RL with the exact-answer verifier (for example GRPO), plus 16k sequences so the hardest traces are kept.

Lessons from the run

  • Megatron-Bridge's offline-pack cache name ignores the data, so a second dataset silently reused an old pack. Fixed with a per-dataset tokenizer path.
  • DeepEP rejects GB200 by device name; HybridEP is the right dispatcher for NVL72.
  • The single-worker packer needs more than 1 h for 230k rows on Grace CPUs, so give it a long limit or run it as a CPU job.
  • Login nodes kill long CPU jobs and cannot import containers. Do that work on compute nodes.
  • Ambiguous wording looks like low accuracy. Read the failures before buying more samples.

Cricket Reasoning · 500K distillation & 32-GPU fine-tune

Hecate · NVIDIA Vera Rubin · October 2026

From 425,119 cricket deliveries to a faster-thinking 27B model

We asked Qwen3.8-27B to reason through half a million cricket arithmetic questions, kept only answers we could prove correct, and taught the model to reach those answers in fewer steps. The result is the same model, but it reasons in 39% fewer tokens and is slightly more accurate.

The pipeline, end to end

Eleven stages, each a SLURM batch job on Hecate. Select a stage to see what it does, or press Play the journey.

In plain words

A student that learns from its own best work

Imagine solving each homework question four times and keeping the shortest attempt that got the right answer. Then study only those clean solutions. That is self-distillation. The teacher and the student are the same model. The checker is plain arithmetic computed from the real scorecard.

Why it is trustworthy

Every training answer is verified

Each question's answer (run rate, required rate, balls to 50…) is computed exactly from the ball-by-ball data. A reasoning trace enters the dataset only if its final number matches. 2,002,672 traces were sampled, and the shortest correct one per question was kept.

What changed

Shorter thinking, same or better answers

On 600 held-out questions from 177 unseen matches: accuracy 97.29% → 97.88%, mean reasoning 748 → 458 tokens, truncated answers 0.38% → 0%. That is roughly 40% less inference compute per question.

Step 1 · Source

Every delivery of every T20 International becomes a question

The source is Valarmathy/CricketData (CC0): 425,119 rows, one row per ball, with the score, wickets, batters, bowler and target at that moment. The job was to create at least one verified reasoning example per row.

Try it · overs notation is the trap

Build a match situation

Cricket writes 14.3 overs to mean 14 overs and 3 balls (87 balls), not 14.3 decimal overs. Models that miss this get the rate wrong. Move the sliders and the exact answers are recomputed the same way cricket_qa.py does.

The questions this row produces

Six question types, chosen per row

Some types are undefined for some rows (e.g. no target in the 1st innings, or a batter on 0). Each row gets the least-used type that is valid for it. 74,881 training rows get a second type, giving exactly 500,000 rows.

Split by match, never by row

All questions from one match land in the same split, so the benchmark matches are truly unseen.

ⓘ
The fixed 600-question benchmark (200 run_rate, 200 chase_rate, 200 milestone) lives entirely in the 177 test matches. Part I and Part II used the same benchmark, so every model is compared on identical questions.

What the model actually sees

A real benchmark prompt. Distractors such as batter scores and the bowler's name are included on purpose, because the model must decide what matters.

Step 2 · Distillation

32 independent vLLM engines, 2 million reasoning traces, 1.9 hours

The bf16 model (51 GB) fits easily on one Rubin GPU (279.5 GiB), so there is no need to split it. Each GPU runs its own vLLM engine on its own shard of questions (data parallelism). There is no GPU-to-GPU traffic, scaling is linear, and a job can be resubmitted with any node count because workers skip question ids that are already sampled.

Inside one vLLM engine

  • Continuous batching. Finished sequences leave and new ones join every step, so the GPU never waits for the longest answer.
  • Prefix caching. The system prompt and match context are shared by the 4 samples of a question and computed once.
  • Hybrid model. Gated DeltaNet layers keep a fixed-size state, and only 16 full-attention layers grow a KV cache, so hundreds of sequences fit per GPU.
  • Resumable. Results are appended after every call. A 100-minute deadline stops new work before the 2-hour job limit.

Step 3 · Fine-tuning

One epoch over 457,689 traces with LoRA, DDP over 32 GPUs, in about 4 hours

The 27B base weights stay frozen. Only small low-rank adapters (LoRA) are trained, which is 217.6 M parameters, 0.79% of the model. Every GPU holds a full model copy and processes its own 8 rows. After each backward pass only the adapter gradients are averaged across the 32 GPUs.

The model: Qwen3.8-27B, a hybrid architecture

64 decoder layers. Three of every four use Gated DeltaNet linear attention (fixed-size state), and every fourth uses full attention. LoRA adapters attach to the attention, linear-attention and MLP projections of every layer. The vision tower is frozen.

Choosing the batch: benchmark on 1 node

30 steps on 20,000 real rows for each variant. Length-grouped batches avoid padding waste.

Batch 16 fails because the output logits alone are 16 × 6,144 × 248,320 vocab × 4 B ≈ 98 GB, plus their gradient.

Memory on one GPU (279.5 GiB)

Worst case: the longest length group (8 × 6,144 tokens). Hover a segment for details.

Network: why LoRA + DDP is cheap

Per step each GPU averages 0.87 GB of adapter gradients (ring all-reduce ≈ 1.7 GB moved). Frozen weights are never sent (_ddp_params_and_buffers_to_ignore), because every rank loads them from Lustre. The all-reduce runs over multi-node NVLink, and the RDMA NICs stayed idle.

Limitations to keep in mind

    
    
      
  • Narrow task. The model was trained only on numeric T20I match-state questions. Use the base model for anything else.
    • 
      
  • Self-distilled. The adapter makes existing behaviour shorter and more consistent. It does not add knowledge the base model lacks.
    • 
      
  • Little headroom. The base model already scores about 97%, so the +0.58-point accuracy gain is small (≈ 1.2 standard errors) but consistent.
    • 
      
  • Benchmark coverage. The benchmark covers 3 of the 6 types. Projection, strike_rate and legal_balls were only checked during generation (97.9–100% base accuracy).
    • 
      
  • Source quirks. Balls-faced counts include some wides, and the questions follow the source numbers.
